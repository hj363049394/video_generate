## 2 架构方案

### 2.1 方案 A：同进程挂载（MVP 推荐）

现有 Bot 是单 asyncio 进程（main.py 启动 radar_push_loop / metrics_collection_loop / Router）。**在同一进程内挂载 FastAPI（uvicorn 共享事件循环）**，API 与 Bot 共享：

- 同一个 SQLite 连接（`state.{bot}.db`）——**彻底规避跨进程写并发**，无需引入消息队列；
- 同一套任务执行器（`_run_task` 的 `asyncio.create_task`）——小程序「照这个写」→ API → 直接入队，进度表实时可见；
- 同一套雷达循环——每日为 Bot 用户与小程序用户**各评各推**（重方案语义不变，推送目标从 adapter 换成订阅消息发送器）。

```
微信小程序（原生 WXML/WXSS）
   │  HTTPS（备案域名 + SSL 证书）※ 小程序 request 合法域名硬要求
   ▼
Nginx（单 VPS 公网部署）
   ├─ /api/*      → FastAPI ⊕ Bot 同进程（asyncio 事件循环共享）
   │                 ├─ 鉴权：wx.login code2session → openid ↔ uid 映射 + 绑定码继承
   │                 ├─ 读接口：清单/任务/发布记录/成本/额度（SQLite 读）
   │                 ├─ 写接口：定位/确认生产/登记链接/重试（复用现有执行器）
   │                 └─ 订阅消息发送器（access_token 中心管理 + 授权额度表）
   ├─ /assets/*   → 静态签名 URL → workspace/{bot}/users/{uid}/{task_id}/images/
   └─ SQLite（WAL，单进程写）—— tasks / user_profiles / cost_log / pending_push
                               / openid_map / sub_auth / quota（新增 3 表）
```

**同进程方案的边界**：HTTP 服务与 Bot 生命周期耦合（Bot 断线重连不影响 HTTP）；单机部署，垂直扩展为主。对 MVP 阶段（用户量 < 数千、日任务 < 数百）完全够用。

### 2.2 方案 B：拆分 API + Worker（演进路线）

触发条件（满足其一）：任务量导致单进程事件循环拥塞；需要多机水平扩展；Bot 与 API 需独立发布。

改造内容：
1. `_run_task` 编排逻辑从 Router 抽出为独立 Worker（内部全是 `to_thread` 调 pipeline 纯函数，抽取难度中）；
2. SQLite → PostgreSQL/MySQL（SQL 语句均为标准写法，迁移成本低）；
3. 任务分发用 DB 轮询即可起步（无需引入 Redis/Kafka）。

**结论：现在不做，但 §7 的代码组织决策按「可拆分」约束写，避免返工。**

### 2.3 数据新增（仅 3 张表，现有表零迁移）

| 新表 | 用途 | 关键字段 |
|---|---|---|
| `openid_map` | openid/unionid ↔ uid 映射 + 绑定码继承记录 | openid, uid, bind_code, bound_at |
| `sub_auth` | 订阅消息授权额度（每次授权 = 1 次可发送） | uid, template_key, remain, updated |
| `quota` | 每日用量（FR-10 闸门） | uid, date, list_viewed, produced |

现有 `tasks / user_profiles / cost_log / pending_push` 结构不变，小程序端直接共用。

### 3.1 账号继承：Bot uid ↔ 小程序 openid（关键缺口）

**问题**：Bot 用户以 `wxid_*` 标识，小程序用户以 openid 标识——**两个命名空间无法自动对上**，PRD FR-01 的「自动继承 Bot 数据」不能凭空实现。

**方案（推荐 a）**：
- **a) 绑定码**（零成本）：老用户在 Bot 发 `/绑定` → 生成一次性 6 位码（15 分钟有效，写 `openid_map.bind_code`）→ 小程序登录后输入 → 合并继承定位/任务/发布记录/成本。新用户走 openid 直接注册，天然隔离。
- b) 手机号快捷绑定（`getPhoneNumber`）——体验好但依赖企业主体认证，与合规链耦合。

### 3.2 订阅消息基础设施（新建，标准工程）

- **授权额度模型**：用户每次点「允许」→ `sub_auth.remain + 1`（按 template_key 记账）；服务端发送前检查余量，成功后 `- 1`。选「总是保持以上选择」的用户后续请求免弹窗，额度自动累积。
- **access_token 管理**：小程序 + 服务号两套 token，中心化获取/缓存/刷新（2h 过期）；存内存即可（单进程）。
- **发送时机**：复用现有 `radar_push_loop` / `metrics_collection_loop` / 任务完成回调，推送目标按用户通道归属路由（Bot 用户走 adapter，小程序用户走订阅消息，互斥——对应 PRD §7.2 同端互斥）。

### 3.3 内容安全接入

- 文本：发布文案交付前调 `msgSecCheck`（用户 openid 必传，微信侧按用户维度风控）；拦截后自动重写一次（重试消耗已计入 FR-10 返还规则）。
- 图片：`mediaCheckAsync` 异步回调，需要在 API 侧加回调端点；MVP 可先只做文本检测 + 生图通道自带审核 `[TBD：验证 ark/redfox 通道审核覆盖]`，图片异步检测作为提审加固项。

## 4 平台合规链：真正的硬前置

**以下四项都不是技术问题，但任何一项缺位都会阻塞上线，且周期不可压缩。建议与技术开发并行启动，主体/备案最先动。**

```
① 注册主体 ──→ ② 域名 + ICP 备案 ──→ ③ 小程序注册 + 类目 ──→ ④ 订阅消息模板申请
（个体户/企业）   （约 1–3 周，管局审核）   （主体认证 300 元/年）      （类目匹配才可选）
      │                │                      │                        │
      ▼                ▼                      ▼                        ▼
  FR-10 付费能力    request 合法域名       提审入口                  FR-07 触达
 （个人主体不可）   （HTTPS 硬要求）      （工具-效率类目）           服务号另需认证（兜底通道）
```

| # | 事项 | 阻塞什么 | 备注 |
|---|---|---|---|
| 1 | **已备案域名 + HTTPS + 公网服务器** | 小程序一切网络请求 | 当前为 localhost 开发态，必须迁到公网 VPS；备案周期最长，**最先启动** |
| 2 | **小程序主体资质** | FR-10 付费升级（微信支付）、部分类目 | 个人主体无法开通微信支付；商业化前提是个体户/企业主体 `[Assumption, TBD：以微信最新政策为准]` |
| 3 | **小程序类目**（工具-效率 / 内容创作） | 提审过审 | AI 生成内容展示 + UGC 检测机制是审核关注点（FR-11 即为此准备） |
| 4 | **订阅消息模板** + 服务号认证 | FR-07 三类模板、沉默用户兜底通道 | 模板文案需与类目匹配；服务号为企业认证（¥300/年）`[TBD]` |

## 5 技术风险清单与缓解

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | 备案/主体周期不可控，阻塞提审 | 高 | 立即启动；技术开发与合规链并行，开发期用测试号 + 本地联调 |
| R2 | SQLite 单写者约束 | 中 | 方案 A 同进程彻底规避；预留方案 B 演进（§2.2），新代码按「单进程写」约束组织 |
| R3 | Bot uid ↔ openid 无法自动继承 | 中 | 绑定码方案（§3.1），过渡期 Bot 内 `/绑定` 引导 |
| R4 | access_token 单点（过期/封禁误处理） | 中 | 中心化管理 + 提前 5 分钟刷新 + 失败重试队列；推送失败一律降级站内待读（PRD FR-07 已定义） |
| R5 | 红狐 API 配额随用户增长线性上涨（雷达每人每关键词搜索 + 按需抓取 + 回采） | 中 | 已有每日去重（同日清单复用）与回采 30 天窗口；额度闸门（FR-10）同时是成本护栏；监控日调用量，超阈值收缩免费档 |
| R6 | 质检报告为纯文本，徽章无结构化数据源 | 低 | `render_quality_report` 增加结构化返回（小改，纯函数） |
| R7 | 静态资产被遍历下载（跨用户访问他人成品） | 中 | 签名 URL（uid + 过期时间 HMAC）；Nginx 层校验，不暴露目录列表 |
| R8 | 视频合成（moviepy/TTS）CPU 占用拖慢同进程事件循环 | 低 | 合成已在 `to_thread`；视频为 P1 低频操作；拥塞时限制并发数 1 |
| R9 | 思源宋体子集化 + HTTPS 托管 | 低 | 标题子集（<100KB）随静态资源发布；loadFontFace 失败静默降级系统字体 |
| R10 | 微信审核驳回（AI 生成内容类） | 中 | FR-11 全量落地（文本检测 + 注销 + 协议）；提审前用「内容安全自检清单」过一遍；预留文案话术说明「辅助创作工具」定位 |

## 6 工作量结构

规模档位：S（1–2 天级）/ M（约一周级）/ L（两周+ 级），按单人全栈投入估算，不含合规链等待期。

| 模块 | 规模 | 说明 |
|---|---|---|
| API 网关层（FastAPI 挂载 + 鉴权 + 12 个左右读写接口） | M | 接口薄壳，逻辑全部复用 |
| 登录 + 绑定码继承 | S | §3.1 |
| 额度闸门（quota 表 + 3 处接线） | S | FR-10 |
| 订阅消息基础设施（模板/授权表/token/发送器/通道路由） | M | FR-07，新建中最重 |
| 内容安全接入（msgSecCheck + 拦截重试流） | S–M | FR-11 |
| 静态资产签名 URL 服务 | S | FR-05 |
| 质检报告结构化改造 | S | FR-05 徽章 |
| 服务号接入（若验证通过） | S–M | 沉默用户兜底 |
| **小程序前端（5 页 + 组件语义规则 + 状态/空态/降级）** | **L** | 最大单项；§6.4 语义规则是验收基准 |
| 分享海报 Canvas | S–M | FR-12 |
| 联调 + 提审材料 + 修审 | M | 合规链并行 |

**复用率结论**：后端生产/数据链路约 80% 直接复用（雷达/仿写/图卡/成本/回采/拉模式/状态机全部现成）；新建工作 ≈ API 壳 + 触达设施 + 前端，其中前端占新增量的一半以上。

## 8 结论

1. **技术上可行且确定性高**：13 项 FR 中 8 项的后端能力已上线可直接接线，其余 5 项（登录/额度/内容安全/订阅消息/资产服务）均为标准工程，无技术不确定性。
2. **真正的关键路径在合规链而非代码**：备案域名、小程序主体、类目、订阅消息模板四项流程依赖应**立即并行启动**——它们决定上线日期，代码反而不会。
